# ADR-0012: An in-process open-model load generator, with saturation judged by the schedule

**Status:** Accepted · **Date:** 2026-08-09

## Context

Phase 3 measures what a web server does, and every module in it needs a load
generator. `docs/BENCHMARK-METHODOLOGY.md` already fixes the hard requirements:

> use an **open-model, constant-rate** generator and measure latency from when a
> request *should* have been sent, not when it was — the coordinated-omission
> correction described by Gil Tene in [wrk2](https://github.com/giltene/wrk2);
> record generator-side CPU utilisation, and emit `GeneratorSaturated` — which
> invalidates the result — if the injector runs out of headroom; support an
> external-generator mode for machines fast enough to outrun a local injector.

The roadmap calls the first deliverable "load generator **selection** + saturation
detection harness", which presumes picking an existing tool — `wrk2`, `k6`,
`vegeta`, `oha`, `bombardier`. That framing needs revisiting against three
constraints this project has already accepted elsewhere:

1. **A single static binary, copied to a server and run.** The product bible
   makes this a hard requirement, and ADR-0011 and the `storage.mixed` fio
   decision have both already been settled on it: a module that only works where
   a particular tool happens to be installed leaves its whole category empty on
   most hosts.
2. **No code path from an HTTP request to a shell.** `crates/darcbench-modules`
   documents that a module "never receives a command line and never constructs
   one", and that this is what makes it safe to expose a start-a-run button to a
   browser. Shelling out to a generator would create exactly that path.
3. **Results must be comparable across machines.** Two runs generated by
   different versions of an external tool, or by tools chosen by whatever the
   operator had installed, are not comparable — the same objection the
   methodology raises against benchmarking WordPress without disclosing the
   cache.

## Decision

**Build the generator in-process**, as `darcbench-modules::loadgen`, rather than
selecting and driving an external one.

**The schedule is a pure function of the request index.** Request `i` is due at
`start + i / rate`, regardless of what happened to requests `0..i`. Nothing the
target does can change when the next request is owed. This is what makes the
model open.

**Two latency series are recorded and both are published:**

| Series | Measured from | What it is |
|---|---|---|
| `service` | actual send | what the target took |
| `response` | *due* time | what a client on a schedule experienced |

Latency metrics are built from `response`. They are equal on an unsaturated
system and diverge exactly when queueing begins.

**Saturation is decided by the schedule, not by generator CPU.** Three
conditions, checked most-specific first:

| Verdict | Condition | What it tells the operator |
|---|---|---|
| `AllWorkersBusy` | starvation on >5% of the schedule | raise the connection count |
| `ScheduleSlip` | mean lateness > half the inter-request period | the injector is behind |
| `RateShortfall` | completions < 95% of what was owed | the target stopped answering |

Any of them emits `WarningCode::GeneratorSaturated`, which is in
`degrades_result()`, so the methodology's "invalidates the result" holds
mechanically rather than by a module remembering to check.

Generator CPU **is** recorded, as `LoadOutcome::generator_cpu_pct`, and reported
in the warning.

**The external-generator mode remains a separate deliverable.** It is the
answer for machines that outrun a local injector, and the saturation detection
above is what tells an operator they have one.

## Rationale

### Why not `wrk2`

`wrk2` is the reference implementation of the correction this generator
implements, and if an external tool were being selected it would be the one.
It is ruled out by constraints 1 and 2, not by its methodology — which is why
the methodology it established is implemented here rather than discarded.

The same argument settled `storage.mixed` against fio: follow the tool's
methodology, do not depend on the tool's presence. Writing it down twice is
deliberate; it is the same trade, and it will come up again in Phase 4.

### Why saturation is judged by the schedule and not by CPU

The methodology names generator-side CPU utilisation as the signal. This ADR
records a deliberate strengthening rather than a substitution.

CPU utilisation is a *proxy* for "the injector ran out of headroom", and it is
wrong in both directions. A generator whose connections are all waiting can fall
badly behind while nearly idle — the failure is in the concurrency budget, not
the CPU. And a generator can sit near its CPU ceiling while holding the schedule
perfectly, which is not a defective measurement.

Missing the schedule is not a proxy for anything. If request 40,000 went out two
seconds late, no latency recorded after it describes the load the run claims to
have offered, whatever the CPU was doing. So the schedule decides and the CPU
figure is published as the explanation of *why*.

### Why an in-process target is acceptable, and where it is not

Serving the objects from inside the agent means `web.static` measures the
machine's HTTP capability — syscalls, loopback, TLS, TCP — under a server that
is identical on every machine. That is the right measurement for a *machine*
benchmark, and it is the same reasoning as the WordPress cache disclosure: a run
against the operator's own nginx would measure their configuration, which is
worth knowing and is not what a comparable machine score can be built from.

It has a real cost that must be disclosed in every such module: the generator
and the target share the machine, so the generator's CPU is taken from the
target's. That is a lower bound on the machine's true capability, not an
estimate of it, and it is the reason the external-generator mode exists.

## Consequences

- One more thing this project maintains itself. The correction is about forty
  lines; the tests that prove it are longer than the implementation, which is
  the right ratio for a component whose failure mode is *plausible wrong
  numbers*.
- Saturation detection is testable without a network, because the generator is
  written against a `LoadTarget` trait rather than an HTTP client. A real server
  that cooperates by being exactly slow enough does not exist; a synthetic
  target that sleeps for a dictated interval does, and it is what proves the
  exit criterion "a saturated generator provably invalidates a result".
- HTTP/2 and HTTP/3 are not reachable this way without adding `h2` and a QUIC
  stack. They are declared unmeasured rather than approximated, in the same
  terms as packet loss in `network.transfer`.
- Every HTTP module must disclose that its generator shared the machine with its
  target. A `web.static` number is a floor.
